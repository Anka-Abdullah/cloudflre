wuzip-bot-runbook.txt - operasi harian bot WhatsApp per nomor (Cloudflare + wuzapi)
=================================================================================
Ruang lingkup : prasyarat, urutan setup per nomor, secret, uji AI, roll-out,
                cara memeriksa, troubleshooting, perintah uji, Turso, Telegram,
                pembayaran (dry-run -> Sumopod), E2E tanpa nomor WA, dan cron.
Pasangan      : wuzip-bot-flow.txt (alur), wuzip-bot-architecture.txt (kontrak).
Path          : relatif terhadap root repo /Users/ank/project/wuzip-bot
Aturan        : dokumen ini TIDAK pernah memuat nilai secret. Hanya nama variabel
                dan contoh perintah yang membaca dari environment.


1. PRASYARAT
------------
  cd cloudflare
  pnpm install

Autentikasi wrangler (sekali per akun Cloudflare), pilih salah satu:

  npx wrangler login
  # atau
  export CLOUDFLARE_API_TOKEN=...        # nilai TIDAK boleh masuk shell history
                                         # produksi: simpan di secret manager

Izin minimum token Cloudflare:
  - Workers Scripts:Edit   (deploy worker + secret)
  - Queues:Edit            (buat queue + DLQ)
  - R2:Edit                (buat bucket)
  - D1:Edit                (buat database + apply migration)
  - KV:Edit                (buat namespace)
  - Account Settings:Read  (opsional; hanya untuk membaca subdomain workers.dev)

Semua perintah wrangler dijalankan dari folder cloudflare/ dan menulis artefaknya
di dalam repo (cloudflare/.wrangler/...), bukan di $HOME (scripts/lib.mjs).


2. URUTAN SETUP PER NOMOR
-------------------------
Nomor = 8-15 digit E.164 tanpa "+" (mis. 6281234567890).

  1) pnpm run new -- --number <nomor>
       Membuat cloudflare/<nomor>/ dari _template/ dan mengisi semua nama unik.
       Opsi: --worker-prefix, --bucket-prefix, --d1-prefix, --kv-prefix, --force.
       Folder yang sudah ada tidak ditimpa tanpa --force.

  2) pnpm run provision -- --number <nomor>
       Membuat queue events, DLQ, bucket R2, database D1, dan KV namespace, lalu
       menulis database_id + id KV yang asli ke cloudflare/<nomor>/wrangler.jsonc.
       Idempoten dan aman diulang: id selalu dibaca ulang dari akun.
       Semua nomor sekaligus: pnpm run provision -- --all
       Durable Object tidak perlu provisioning (dibuat saat deploy pertama).

  3) pnpm run secrets -- --number <nomor> [opsi]
       Mengisi secret. Lihat bagian 3.

  4) pnpm run migrate -- --number <nomor>
       Menerapkan skema D1 (shared/src/bot/migrations/0001_init.sql dan
       0002_payment_outbox.sql) ke database remote. Tambahkan --local untuk
       database lokal saja. Skema Turso TIDAK lewat perintah ini: lihat bagian 10.

  5) Deploy atau jalankan lokal:
       pnpm run deploy -- --number <nomor>
       pnpm run dev    -- --number <nomor> [--port 8790]
       dev mensimulasikan queue, R2, D1, KV, dan Durable Object; state lokal ada
       di cloudflare/.wrangler/state.

  6) Daftarkan di dashboard wuzapi untuk nomor itu:
       Webhook URL    : https://<worker>.<subdomain-akun>.workers.dev/ingest/<INGEST_TOKEN>
       HMAC Key       : nilai yang sama dengan secret WUZAPI_HMAC_KEYS
       Webhook Events : All, atau subset (mis. Message,Connected,Disconnected)
       WEBHOOK_FORMAT : "json" disarankan (metadata media ikut terbaca).
       Lalu isi WUZAPI_API_BASE di wrangler.jsonc ke domain publik wuzapi nomor
       ini (HTTPS, tanpa trailing slash) dan deploy ulang.

Urutan wajib: new -> provision -> secrets -> migrate -> deploy. Deploy sebelum
provision ditolak wrangler karena database_id masih placeholder nol.


3. SECRET
---------
3.1 Daftar lengkap (14 nama; daftar ENV_SECRETS di scripts/instance.mjs)

+-----------------------------+----------------------+---------------------------------+
| Nama                        | Wajib untuk          | Fungsi                          |
+-----------------------------+----------------------+---------------------------------+
| INGEST_TOKEN                | selalu               | token di path /ingest/<token>   |
| WUZAPI_HMAC_KEYS            | selalu (HMAC != off) | key HMAC; boleh beberapa,       |
|                             |                      | dipisah koma, untuk rotasi      |
| DOWNSTREAM_HMAC_KEY         | BOT_MODE=off         | tanda tangan relay ke bot lama  |
| ALERT_WEBHOOK_URL           | opsional             | tujuan alert saat DLQ           |
| WUZAPI_TOKEN                | BOT_MODE != off      | header "token" ke REST wuzapi   |
| AI_API_KEY                  | BOT_MODE != off      | bearer ke endpoint AI           |
| TURSO_DATABASE_URL          | checkout/order       | URL libsql (bagian 10)          |
| TURSO_AUTH_TOKEN            | checkout/order       | token libsql (bagian 10)        |
| PAYMENT_API_KEY             | bayar live           | kunci gateway Sumopod (bag. 12) |
| PAYMENT_CALLBACK_SECRET     | bayar live           | verifikasi callback gateway     |
| TELEGRAM_BOT_TOKEN          | kartu admin          | bot token Telegram (bagian 11)  |
| TELEGRAM_CHAT_ID            | kartu admin          | chat penerima kartu admin       |
| TELEGRAM_WEBHOOK_SECRET     | kartu admin          | X-Telegram-Bot-Api-Secret-Token |
| ADMIN_API_KEY               | /admin/*             | bearer untuk /admin/*           |
+-----------------------------+----------------------+---------------------------------+
botReadiness() menghitung lima nama berikut: WUZAPI_API_BASE (var), WUZAPI_TOKEN,
AI_BASE_URL (var), AI_MODEL (var), dan AI_API_KEY, ditambah binding BOT_DB dan
CHAT_COORDINATOR. Selama salah satunya belum ada, /healthz melaporkan
bot.ready=false dan menyebut namanya di bot.missing / bot.missingBindings.

3.2 Cara mengisi (urut dari yang paling aman)

  a. Dari environment (disarankan; nilai tidak muncul di shell history):
       export AI_API_KEY=...
       export WUZAPI_TOKEN=...
       pnpm run secrets -- --number <nomor> --from-env
     --from-env membaca semua nama di daftar 3.1 yang ada dan tidak kosong.
     Pratinjau tanpa mengirim apa pun:
       pnpm run secrets -- --number <nomor> --from-env --dry-run

  b. Flag per secret (nilai ikut tercatat di history shell - hati-hati):
       pnpm run secrets -- --number <nomor> --hmac-key "<32+ karakter>"
       pnpm run secrets -- --number <nomor> --wuzapi-token "<token>"
     Flag lain: --downstream-key, --alert-webhook-url, --ai-api-key, --turso-url,
     --turso-token, --payment-key, --payment-callback-secret, --telegram-token,
     --telegram-chat-id, --telegram-webhook-secret, --admin-key.

  c. Pasangan eksplisit:
       pnpm run secrets -- --number <nomor> --set ADMIN_API_KEY=<nilai>

  d. Dibuatkan (random 32 byte):
       pnpm run secrets -- --number <nomor> --generate ADMIN_API_KEY
     Nilai yang di-generate TIDAK pernah dicetak, hanya jumlah karakternya.
     Pakai hanya untuk secret yang tidak perlu Anda salin ke sistem lain.
     Untuk WUZAPI_HMAC_KEYS jangan pakai --generate: nilai yang sama harus
     diketik di dashboard wuzapi, jadi pakai --hmac-key.

  e. Tanpa opsi apa pun:
       pnpm run secrets -- --number <nomor>
     Selalu memastikan INGEST_TOKEN ada (nilai lama dari .dev.vars dipertahankan
     kecuali --rotate-ingest-token), lalu mencetak URL webhook dan daftar secret
     bot yang masih kurang.

  f. Melihat nama yang sudah ada (nilai tidak pernah bisa dibaca kembali):
       pnpm run secrets -- --number <nomor> --list

3.3 Rotasi dan kebersihan

  - Ganti token URL kapan saja: pnpm run secrets -- --number <nomor>
    --rotate-ingest-token, lalu perbarui Webhook URL di dashboard wuzapi.
  - Rotasi HMAC tanpa downtime: WUZAPI_HMAC_KEYS menerima beberapa key dipisah
    koma. Set "key-lama,key-baru" di worker -> ganti key di dashboard -> hapus
    key lama.
  - Setelah setup selesai, rotasi AI_API_KEY / WUZAPI_TOKEN bila nilainya pernah
    lewat shell history atau chat.
  - .dev.vars dan .dev.vars.* di-gitignore (hanya *.example yang di-commit).
    Jangan pernah menempelkan nilai asli ke wrangler.jsonc, README, atau doc ini.
  - Nilai lokal untuk dev: cp cloudflare/<nomor>/.dev.vars.example
    cloudflare/<nomor>/.dev.vars lalu sesuaikan (nilainya palsu).


4. UJI AI (SMOKE) - FASE 0
--------------------------
  export AI_API_KEY=...
  pnpm run smoke:ai -- --number <nomor>
  # atau: pnpm run smoke:ai -- --base-url https://.../v1 --model <id> --api-key ...

Sumber key, berurutan: --api-key, $AI_API_KEY, <nomor>/.dev.vars, lalu
cloudflare/.dev.vars. Key tidak pernah dicetak dan tidak ditulis ke disk.

Tiga pertanyaan yang dijawab, plus cara membacanya:

+------------------+--------------------------------------+---------------------------+
| Pemeriksaan      | Hasil PASS                           | Hasil WARN / FAIL         |
+------------------+--------------------------------------+---------------------------+
| text             | model mengembalikan teks; dialog     | FAIL: endpoint/key/model  |
|                  | dasar hidup                          | salah atau timeout        |
| function calling | model mengeluarkan tool_calls asli   | WARN: model menjawab teks;|
|                  | -> agent boleh pakai native tool     | pakai mode JSON + parser  |
|                  | calling (rencana Q7=A)               | internal (risiko R1)      |
| JSON mode        | response_format json_object          | WARN: parser harus        |
|                  | mengembalikan JSON yang bisa diparse | defensif; fallbackReply   |
|                  |                                      | tetap penting             |
+------------------+--------------------------------------+---------------------------+
Blok "verdict" merangkum ketiganya dan mencetak saran konfigurasi:
  native tool call OK   -> "leave AI tool calling on (plan Q7=A, native)"
  tidak tersedia        -> "use JSON mode + internal parser" (risiko R1)
Exit code: 0 = dialog bekerja, 1 = dialog gagal, 2 = tidak ada API key.
Tambahkan --json untuk ringkasan yang bisa dibaca mesin.

Hasil live (FASE 3): native tool calling AKTIF, jadi AI_TOOLS_MODE=native.
Model mengirim reasoning_content - diabaikan, tidak pernah ke customer.
Budget: AI_MAX_TOKENS=2048 (sementara). max_tokens 128 terbukti terlalu kecil:
jawaban datang kosong dengan finish_reason "length" dan tampak seperti model
tidak sanggup, padahal hanya terpotong. Skrip kini mengulang sekali dengan
budget 2x sebelum menyimpulkan gagal.

Arti penting: bila native tool calling tidak tersedia, agent memakai jalur JSON
mode. Uji ini yang menentukan jalur mana yang dipakai, bukan asumsi. Sejak FASE 3
pipeline benar-benar memanggil AI (cloudflare/shared/src/bot/agent/run.ts); log
"ai_unavailable" hanya muncul bila AI_BASE_URL/AI_API_KEY kosong, dan pada kasus
itu responder turun ke fallbackReply() deterministik.


5. ROLL-OUT PER NOMOR (SHADOW DULU, JANGAN LANGSUNG ON)
-------------------------------------------------------
  1. Set BOT_MODE=shadow di cloudflare/<nomor>/wrangler.jsonc, lalu
     pnpm run deploy -- --number <nomor>.
     Pipeline berjalan penuh (filter, policy, lock, history, AI, tools) tetapi
     deliverOutbound() tidak mengirim apa pun; balasan yang
     seharusnya dikirim muncul di log sebagai outbound_suppressed_shadow.
  2. Amati pnpm run tail -- --number <nomor> selama 1x24 jam. Yang diperiksa:
       - event_received vs event_done: apakah semua pesan customer berakhir selesai;
       - event_filtered: apakah ada customer 1:1 yang ikut terbuang;
       - event_suppressed: apakah no_ai/suppressed sesuai keinginan;
       - event_duplicate / event_locked: apakah lock dan idempotensi bekerja;
       - outbound_suppressed_shadow: apakah isi balasan sudah benar.
  3. Bila balasan sudah benar: set BOT_MODE=on untuk SATU nomor, deploy, dan
     pantau log + keluhan customer. Pastikan TIDAK muncul bot_degraded_shadow
     (kalau muncul, config belum lengkap dan tidak ada balasan yang keluar).
  4. Setelah satu nomor stabil (mis. beberapa hari), baru naikkan nomor
     berikutnya satu per satu. Jangan menyalakan beberapa nomor sekaligus.
  5. Rollback kapan saja: set BOT_MODE=off lalu deploy. Nomor kembali menjadi
     relay murni (atau diam bila RELAY_MODE=observe / DOWNSTREAM_URL kosong)
     tanpa perlu menyentuh wuzapi, queue, atau data.
Catatan: BOT_MODE ada di vars wrangler.jsonc, jadi setiap perubahan butuh
deploy. Selama BOT_MODE=off, D1/KV/DO tidak wajib ada.


6. CARA MEMERIKSA
-----------------
6.1 GET /healthz  (publik, tidak pernah membocorkan nilai secret)

  curl -s https://<worker>.<subdomain>.workers.dev/healthz | jq

+---------------------------+------------------------------------------------------+
| Field                     | Arti                                                 |
+---------------------------+------------------------------------------------------+
| ok                        | true selama config bisa dimuat                       |
| slug                      | INSTANCE_SLUG nomor ini                              |
| hmacMode                  | strict / optional / off                              |
| hmacKeys                  | JUMLAH key di WUZAPI_HMAC_KEYS (bukan nilainya)      |
| mediaMode                 | r2 / reject                                          |
| relayMode                 | relay / observe                                      |
| botMode                   | off / shadow / on                                    |
| knowledgeMode             | auto / kv_inline / r2_d1_fts                         |
| aiModel                   | id model yang dikonfigurasi (bukan rahasia)          |
| bindings.EVENTS           | binding queue events ada?                            |
| bindings.DLQ              | binding queue DLQ ada?                               |
| bindings.MEDIA            | binding bucket R2 ada?                               |
| bindings.BOT_DB           | binding D1 ada? (wajib untuk BOT_MODE != off)        |
| bindings.KNOWLEDGE_KV     | binding KV ada? (FASE 3)                             |
| bindings.CHAT_COORDINATOR | binding Durable Object ada? (lock + rate limit)      |
| bot.ready                 | true = pipeline bisa menjawab tanpa kehilangan pesan |
| bot.missing               | daftar NAMA config yang masih kosong                 |
| bot.missingBindings       | daftar BINDING yang belum dideklarasikan             |

| downstreamConfigured      | DOWNSTREAM_URL terisi                                |
| r2PublicBaseUrl           | R2_PUBLIC_BASE_URL terisi (bool)                     |
+---------------------------+------------------------------------------------------+
bot.ready=false dengan bot.missing=["AI_API_KEY"] berarti endpoint AI belum
lengkap: pipeline masih jalan, tetapi balasan yang keluar adalah fallback
deterministik. bot.ready=false karena missingBindings=["BOT_DB","CHAT_COORDINATOR"]
berarti provision bagian D1/DO belum jalan - jangan nyalakan BOT_MODE=on.
PENTING: BOT_MODE=on + bot.ready=false TIDAK menghasilkan balasan. Pipeline
otomatis berjalan sebagai shadow (log bot_degraded_shadow) supaya balasan
fallback generik tidak pernah sampai ke customer; lengkapi dulu config/binding
lalu deploy ulang.

6.3 Queue dan arsip

  - Backlog, retry, dan DLQ terlihat di dashboard Cloudflare (Queues).
  - Arsip DLQ ada di bucket R2 nomor itu: _dlq/<slug>/<YYYY-MM-DD>/<messageId>.json
    (berisi record + envelope asli).
  - Payload besar ada di events/<slug>/<YYYY>/<MM>/<DD>/<uuid>.json|.form.
  - ALERT_WEBHOOK_URL, bila diisi, menerima satu notifikasi per record DLQ.

10. TURSO (ORDER + PAYMENT)
---------------------------
Database order/payment TIDAK memakai Cloudflare. Worker menghubunginya lewat
HTTP libsql (`@libsql/client/web`) memakai secret per nomor; D1 tetap milik bot
(history, cart, outbox), Turso milik order (customers, orders, order_items,
payments). Tidak ada resource bersama antar nomor: TURSO_* adalah secret per
nomor, jadi satu nomor boleh memakai database sendiri.

10.1 Mengisi kredensial

  export TURSO_DATABASE_URL=libsql://<host-anda>
  export TURSO_AUTH_TOKEN=<token-anda>
  pnpm run secrets -- --number <nomor> --from-env

  Nilai TIDAK boleh masuk wrangler.jsonc (vars terlihat di repo). Untuk dev
  lokal, isi cloudflare/<nomor>/.dev.vars (git-ignored, permission 600);
  untuk produksi, pakai `pnpm run secrets -- --from-env` seperti di atas.

10.2 Schema dibuat otomatis

  Tidak ada langkah manual dan tidak ada konsol: schema diterapkan worker saat
  order/checkout pertama menyentuh database (ensureTursoSchemaOnce; DDL di
  shared/src/bot/payment/schema.ts, semuanya CREATE TABLE IF NOT EXISTS).
  Tabel: customers, orders, order_items, payments. Semua uang INTEGER rupiah;
  ref / client_ref / kode_pesanan / kode_bayar UNIQUE sehingga kiriman ulang
  tidak pernah membuat baris kedua.

  Status order yang sah (orders.status):
    creating, awaiting_approval, approved, rejected, pending, paid, expired,
    failed, superseded
  Perubahan status hanya lewat UPDATE kondisional (WHERE status IN (...)), jadi
  callback yang datang dua kali adalah no-op, bukan transisi kedua.

10.3 Verifikasi

  pnpm run smoke:turso -- --number <nomor>
    - dengan kredensial  : connect + apply schema + insert order dummy + select
                           + idempotensi + delete dummy ke database SUNGGUHAN.
    - tanpa kredensial   : DDL dan statement yang SAMA dijalankan pada SQLite
                           lokal lewat node:sqlite, jadi schema tetap terbukti
                           sebelum akun Turso ada.
    Opsi: --url <libsql://...>, --token <token>, --local-secrets, --keep.

  Dari worker (read-only, tidak membocorkan nilai secret):

    curl -s -H "Authorization: Bearer $ADMIN_API_KEY" \
      https://<worker>/admin/status | jq .payment
    -> provider, dryRun, tursoConfigured, tursoError, tables

10.4 Catatan

  - `pnpm run migrate` HANYA untuk D1 (bot). Tidak ada perintah migrasi Turso:
    schema idempoten dan dijalankan sendiri oleh worker.
  - TURSO_* adalah secret PER NOMOR, jadi pemisahan database antar nomor bisa
    dilakukan kapan saja tanpa mengubah kode.
  - Rekonsiliasi status pembayaran berjalan di cron (bagian 14); saat
    PAYMENT_DRY_RUN=true job itu di-skip karena tidak ada gateway untuk ditanya.


11. TELEGRAM (KARTU APPROVAL ADMIN)
-----------------------------------
Dipakai untuk kartu "Terima / Tolak / Ubah Biaya" (order yang ongkirnya tidak
termasuk), notifikasi order, dan alert DLQ. Tanpa Telegram, approval bisa
dikerjakan lewat endpoint admin (11.4).

11.1 Membuat bot dan mengisi variabel

  1. Buat bot lewat @BotFather -> dapat TELEGRAM_BOT_TOKEN.
  2. Admin chat 8689683590 HARUS menekan /start di bot itu. Bot menjawab
     "Bot aktif. TELEGRAM_CHAT_ID=<id>"; angka itulah isi TELEGRAM_CHAT_ID.
     (Telegram tidak mengizinkan bot mengirim pesan lebih dulu, jadi tanpa
     langkah ini kartu approval tidak akan pernah sampai.)
  3. export TELEGRAM_BOT_TOKEN=...
     export TELEGRAM_CHAT_ID=<id dari langkah 2>
     export TELEGRAM_WEBHOOK_SECRET=<string acak>
     pnpm run secrets -- --number <nomor> --from-env
  4. Set TELEGRAM_ENABLED=true di wrangler.jsonc, lalu
     pnpm run deploy -- --number <nomor>.

11.2 Mendaftarkan webhook

  Webhook Telegram harus menunjuk ke worker nomor ini:

    curl -s "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/setWebhook" \
      -d "url=https://<worker>/webhooks/telegram" \
      -d "secret_token=$TELEGRAM_WEBHOOK_SECRET"

  Worker memverifikasi header X-Telegram-Bot-Api-Secret-Token terhadap
  TELEGRAM_WEBHOOK_SECRET; tidak cocok -> 401 dan tidak ada yang diproses.

11.3 Alur tombol

  Terima      -> order approved -> link pembayaran dibuat dan dikirim
  Tolak       -> order rejected -> alasan dikirim SEKALI ke customer
  Ubah Biaya  -> kartu meminta balasan (force_reply); admin membalas angka,
                 additional_fee diperbarui lalu link dibuat
  Kartu yang sudah diputus tidak diproses dua kali: tiap update Telegram
  diklaim lewat processed_events (delivery id dari update id).

11.4 Tanpa Telegram (atau saat darurat)

  GET  /admin/orders/<kode>          lihat order + item + payment
  POST /admin/orders/<kode>/approve  setujui; body opsional {"additionalFee": N}
  POST /admin/orders/<kode>/reject   tolak;  body {"reason": "..."}
  POST /admin/outbox/flush           kirim isi outbox sekarang
  GET  /admin/status                 ringkasan payment/telegram/outbox
  POST /admin/contacts/sync          tarik kontak + saklar no_ai sekarang
  Semua butuh header: Authorization: Bearer $ADMIN_API_KEY
  (ADMIN_API_KEY kosong -> endpoint menjawab 503, bukan terbuka.)


12. PEMBAYARAN: DRY RUN -> SUMOPOD
----------------------------------
12.1 Dry-run (default, tanpa akun gateway)

  PAYMENT_DRY_RUN=true membuat create_payment_link menghasilkan
  {PUBLIC_BASE_URL}/dry-run/<kode_bayar> dan TIDAK memanggil Sumopod.
  Isi PUBLIC_BASE_URL dengan URL worker nomor ini; kalau kosong tautannya
  relatif (/dry-run/<kode_bayar>) dan tidak bisa dibuka customer.

  GET /dry-run/<kode_bayar> menampilkan order + tiga tombol simulasi:
    Bayar sekarang (simulasi) / Tandai kedaluwarsa / Tandai gagal
  Tombol itu mengirim payment.event ke queue yang SAMA seperti callback asli
  (delivery id deterministik <kode_bayar>:<status>:dry-run), sehingga jalur
  paid -> nota PDF bisa diuji penuh tanpa gateway.

12.2 Live Sumopod

  PAYMENT_API_KEY           kunci merchant (secret)
  PAYMENT_CALLBACK_SECRET   rahasia verifikasi callback (secret)
  PAYMENT_API_BASE          default https://api-pay-sandbox.sumopod.com
  PAYMENT_CREATE_PATH       default /v1/payments
  PAYMENT_STATUS_PATH       default /v1/payments/{ref}
  PAYMENT_DRY_RUN           false

  Bentuk HTTP Sumopod BELUM diverifikasi (FASE 5 dikerjakan tanpa kredensial).
  Yang sudah pasti dari kode: buat link = POST {PAYMENT_API_BASE}
  {PAYMENT_CREATE_PATH} dengan bearer PAYMENT_API_KEY; tanya status = GET
  {PAYMENT_STATUS_PATH} dengan {ref} diganti provider ref. Kalau kontrak
  Sumopod berbeda, dua var itulah yang disesuaikan - bukan kodenya.

  Callback gateway diarahkan ke:

    https://<worker>/payment/callback

  Verifikasi: HMAC-SHA256 atas body MENTAH (hex), dibandingkan konstan-waktu.
  Header yang dicoba berurutan: x-callback-signature, x-signature,
  x-sumopod-signature, x-payment-signature; kalau gateway menaruh tanda tangan
  di body, field signature / sign / hmac juga diterima. Bila Sumopod memakai
  nama header lain, satu-satunya tempat yang perlu diubah adalah
  SIGNATURE_HEADERS di shared/src/bot/payment/provider.ts.
  PAYMENT_CALLBACK_SECRET kosong -> 503; signature salah -> 401. Keduanya tidak
  mengubah status order.

  Rekonsiliasi otomatis: saat PAYMENT_DRY_RUN=false cron menanyakan status order
  'pending' ke gateway lalu mengirim payment.event dari jawabannya (bagian 14).

14. CRON
--------
wrangler.jsonc tiap nomor mendeklarasikan satu trigger:

  "triggers": { "crons": ["*/1 * * * *"] }

Setiap menit worker menjalankan job berikut. Satu job yang gagal TIDAK
membatalkan job lain; setiap job mencetak satu baris log cron_job (atau
cron_job_failed) berisi ms dan ringkasannya.

+---------------------+------------------------------------------------------+
| job                 | isi                                                  |
+---------------------+------------------------------------------------------+
| outbox_flush        | klaim lease lalu kirim baris outbox yang siap        |
| expire_orders       | order lewat expires_at -> expired + kabari customer  |
| reconcile_payments  | tanya status ke gateway (DI-SKIP saat dry-run)       |
| contact_sync        | GET /user/contacts -> contacts + saklar no_ai        |
| retry_unreplied     | chat aktif yang belum dibalas -> satu pesan sopan    |
| prune_history       | harian: history 90 hari + kartu Telegram 72 jam      |
+---------------------+------------------------------------------------------+

Interval:
  CONTACT_SYNC_INTERVAL_MINUTES  default 10; 0 = mati
  RETRY_UNREPLIED_MINUTES        default 0 (mati)
  prune_history                  harian (klaim 24 jam sekali)
Job berinterval diklaim lewat tabel D1 cron_state (UPDATE kondisional), jadi dua
invokasi cron yang tumpang tindih tidak menjalankan job yang sama dua kali.

Memicu manual di dev - butuh wrangler dev dengan --test-scheduled (skrip E2E
memakainya):

  curl "http://127.0.0.1:8790/__scheduled?cron=*+*+*+*+*"

Log yang perlu dilihat: cron_job (job, ms, hasil) dan cron_job_failed (job,
error). Saat Turso belum dikonfigurasi, expire_orders dan reconcile_payments
melaporkan skipped: turso_not_configured - itu normal, bukan kegagalan.
